Keyboard and Screen Reader Lab

Task 1: implement keyboard navigation and screen reader support with ARIA. Each component below lists what to test and which ARIA it uses. Prefer native HTML; ARIA appears only where HTML has no equivalent.

    Skip link (SC 2.4.1 Bypass Blocks)

    The first focusable element on this page is "Skip to main content". It is hidden off-screen until it receives focus, then it jumps keyboard users past the header and tabs.

    What to test

    • Press the button, then press Tab once: the link appears.
    • Press Enter: focus lands on the main region.

    Roles, states, properties

    • Plain <a href="#main">: no ARIA needed. Target has tabindex="-1" so it can receive focus.

    Tabs (APG Tabs pattern)

    What to test

    • Tab enters the tab list on the selected tab only, and the next Tab goes to the panel.
    • ← → move and activate (wrapping); Home/End jump to first/last.

    Roles, states, properties

    • role=tablist with aria-label; role=tab with aria-selected, aria-controls; role=tabpanel with aria-labelledby.
    • Roving tabindex (0 on selected, -1 on others).

    Screen readers convert on-screen content to synthetic speech. Rate, voice and punctuation are user-configurable.

    Refreshable braille displays show the same text and role information as speech, line by line.

    Browse (virtual cursor) mode lets users read and jump by headings, landmarks and links; focus mode passes keys to widgets.

    Accordion (APG Accordion pattern)

    What to test

    • Each header is a button in the Tab order. Enter or Space toggles it.
    • The screen reader announces "collapsed"/"expanded".

    Roles, states, properties

    • Native <button> inside a heading, with aria-expanded and aria-controls. Collapsed panels use the hidden attribute, which removes them from the accessibility tree.

    The text a screen reader announces for a control, computed from content, label, aria-label or aria-labelledby.

    Only when no native element expresses the semantics. First rule of ARIA: if you can use native HTML, do.

    The sequence in which Tab visits controls. It should follow the visual and logical reading order (SC 2.4.3).

    Modal dialog (APG Dialog pattern)

    What to test

    • Open: focus moves into the dialog (to the email field).
    • Tab/Shift+Tab cycle inside; the page behind is inert.
    • Esc closes; focus returns to the trigger.

    Roles, states, properties

    • role=dialog, aria-modal="true", aria-labelledby (title), aria-describedby (description).
    • The rest of the page gets the inert attribute, and a keydown handler also traps Tab as a fallback.

    Dropdown menu button (APG Menu Button pattern)

    What to test

    • Enter, Space or ↓ opens and focuses the first item; ↑ opens on the last.
    • ↑ ↓ move (wrapping), Home/End jump, letters jump to a matching item.
    • Esc closes and returns focus to the button. Tab closes the menu.

    Roles, states, properties

    • Button: aria-haspopup="menu", aria-expanded, aria-controls. List: role=menu, items role=menuitem with tabindex="-1" (focus is moved by script).

    Form with validation (SC 1.3.1, 3.3.1, 3.3.2, 4.1.3)

    What to test

    • Submit empty: focus jumps to the error summary; each link focuses its field.
    • Each invalid field announces its error as its description.
    • Fix a field: its error clears; a successful submit is announced by the status region.

    Roles, states, properties

    • <label for> for names; aria-required="true" (we skip native required and use novalidate so our accessible messages replace the browser bubble); aria-invalid; aria-describedby to hint and error text; autocomplete tokens (SC 1.3.5); role=status for results.

      Toast / status message (SC 4.1.3 Status Messages)

      Messages that do not take focus must still be announced. The live region exists in the DOM before its text changes. Messages stay until dismissed, so nobody is timed out (SC 2.2.1).

      What to test

      • Activate the button: a screen reader reads the message without focus moving.

      Roles, states, properties

      • role="status" (implicit aria-live="polite", aria-atomic="true"). Use role="alert" only for urgent errors.

      Sortable data table (SC 1.3.1)

      What to test

      • Screen reader table navigation (Ctrl+Alt+Arrows in NVDA/JAWS) reads the column header with each cell.
      • Activate a column button: the sort is announced.

      Roles, states, properties

      • <caption>, <th scope="col">, and aria-sort ("ascending"/"descending") on the one sorted header. The sort control is a native button.

          Audit Report and Checklist

          Be realistic about tools. Automated checkers (axe DevTools, Lighthouse, WAVE) only detect a portion of WCAG problems. Published estimates vary roughly from about a third to a little over half, depending on the study and how issues are counted. Manual testing with keyboard, zoom and real screen readers is required, and so is human judgement (is the alt text useful? is the focus order logical?).

          Test-method guide

          1. Unplug or ignore the mouse. Start at the address bar and press Tab.
          2. Check: skip link appears; focus order matches reading order; focus is always visible; nothing needs a mouse; no traps (Esc/Tab always leave).
          3. Operate every widget: links with Enter; buttons with Enter/Space; menus, tabs, sliders with arrows; dialogs trap focus and return it.

          • NVDA (Windows, free) with Firefox or Chrome: Ctrl stops speech; H headings, D landmarks, K links, F form fields, T tables, NVDA+F7 elements list.
          • VoiceOver (macOS) with Safari: Cmd+F5 toggles; VO+U rotor. On iOS: Settings, Accessibility, VoiceOver; swipe and rotor.
          • TalkBack (Android) with Chrome: swipe right/left to move; explore by touch; local context menu for headings and links.
          • JAWS with Chrome/Edge is also widely used in the workplace; behaviour can differ from NVDA, so test more than one pairing.
          • Listen for: meaningful names and roles, states (expanded, selected, invalid), headings/landmarks structure, announcements of dynamic updates.

          • Browser zoom to 200% (SC 1.4.4) and 400% at 1280px width, equal to 320 CSS px (SC 1.4.10): no horizontal scrolling (except data tables, maps, etc.), nothing clipped or overlapping.
          • Increase only the text size or apply a text-spacing bookmarklet (SC 1.4.12).
          • Try the OS magnifier (Windows Win++, macOS Zoom) and check that focus stays on screen.

          • Colour Contrast Analyser (TPGi), the WebAIM Contrast Checker, or the browser DevTools colour picker (shows the ratio).
          • Check text (4.5:1, large 3:1), UI components and graphics (3:1), focus indicators and states (hover, focus, disabled is exempt). Text on images/gradients needs manual sampling of the worst spot.

          • axe DevTools (browser extension): low false-positive rate; includes "needs review" items.
          • Lighthouse (in Chrome DevTools): runs a subset of axe rules; a score of 100 does not mean accessible.
          • WAVE (WebAIM): visual overlay of errors, alerts and structure.
          • Use them first to catch the obvious, then do the manual tests above. Treat "no errors found" as the start of testing, not the end.

          Overview: how the three tasks map to the modules

          • Task 1, keyboard and screen reader support with ARIA: Module 1 is a gallery of APG-pattern components with the key log and ARIA Inspector.
          • Task 2, testing with contrast checkers and magnification: Module 2 holds the WCAG contrast calculator, page scanner, colour-blindness filters, zoom, reflow, text-spacing and lens tools.
          • Task 3, modifying an existing UI to meet WCAG 2.1 AA: Module 3 has a Before page with 25 failures, a fixed After page, the issue tracker with diffs, and real page-level demos.
          • Module 4 turns what you find into a checklist-based audit report.
          • Architecture: one HTML file, inline CSS and vanilla JavaScript, state in memory only. Themes swap CSS variables, so contrast guarantees travel with the theme.

          How to test this app

          Keyboard-only walkthrough

          1. Reload, then press Tab once: "Skip to main content" appears. Press Enter: focus lands on the main region.
          2. Tab to the module tabs. Use ← → Home End to switch; only the selected tab is a Tab stop.
          3. In Module 1, open the dialog, press Tab around it, then Esc: focus returns to the button. Open the menu with ↓, move with arrows, close with Esc.
          4. Submit the empty form: focus goes to the error summary. Watch the key log to confirm the focus order is logical.
          5. In Module 3, Before view, try to Tab out of the date field (you cannot; press Esc).

          Screen reader walkthrough

          1. Start NVDA (free), Narrator (Win+Ctrl+Enter) or VoiceOver (Cmd+F5).
          2. List headings and landmarks (NVDA: H, D). Confirm one h1 and a logical outline.
          3. Trigger Save draft, sort the table and submit the form: each result should be spoken without focus moving.
          4. In Module 3, compare Before and After: icon buttons, unlabeled fields, the table and the cart message.

          Zoom and contrast walkthrough

          1. Set browser zoom to 200%, then 400%: the lab must not scroll horizontally (data tables and previews scroll inside their own regions).
          2. Switch the Theme between Light, Dark and High contrast, and read everything.
          3. In Module 2, note the default #767676 on #ffffff passes at 4.54:1, then change the text colour to #777777 (4.47:1: fails AA normal text). Use Suggest and Apply.
          4. Run the page scanner, then try the colour-blindness filters, 200% zoom, the 320 px reflow test, text spacing and the lens (N/P steps through controls).

          Known limitations

          • It cannot replace testing with real assistive technology (NVDA, JAWS, VoiceOver, TalkBack), a real OS magnifier, or real users.
          • Colour-blindness filters are approximations. Zoom, reflow and lens are simulations built with CSS transforms, not true browser zoom.
          • The scanner checks text colours and form borders only. It ignores background images, gradients, opacity and pseudo-elements other than placeholders.
          • The accessible name shown in the log and inspector is a simplified computation, not the full accname algorithm.
          • The checklist is self-reported. A completed checklist is not a conformance claim, and automated tools find only a portion of issues.
          • An automated run (axe, Lighthouse, WAVE) WILL report errors inside the Module 3 "Before" sample: missing alt text, unnamed buttons, low contrast, positive tabindex. That sample is the course material, not a defect; every element outside it passes axe Core's WCAG 2.1 A and AA rules.
          • Verified with axe Core and a scripted keyboard pass in headless Chromium (Edge). Screen reader behaviour varies by browser pairing; verify yours.
